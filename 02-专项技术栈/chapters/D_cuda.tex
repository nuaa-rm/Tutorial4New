\subsubsection{CUDA 能做什么：先看数据能不能分工}
上一章我们已经让 PyTorch 使用 GPU，不过调用 \texttt{to('cuda')} 并没有告诉我们它怎样分配工作。接下来，我们自己写一个小算子，看看数据怎样送进去、线程怎样找到自己的位置，以及结果什么时候才真正算完。你以后不一定天天手写 CUDA，但如果只会看“显卡利用率”，遇到速度问题就容易把所有锅都甩给显卡。

CUDA（Compute Unified Device Architecture）是 NVIDIA 在 2006 年推出的通用并行计算平台与编程模型。我们用接近 C++ 的语法写设备函数（kernel），让许多线程分别处理数据。图像阈值、滤波和网络中的大批量数值计算常能这样分工，不过“有很多数据”不等于“每项都独立”。例如前缀和 $s_i=\sum_{j=0}^{i}x_j$ 就有跨元素关系，不能让每个线程随便读前一项还没完成的结果。
\begin{example}[在 CPU 上先看清依赖]
本章工程位于本卷 \path{examples/cuda/vector-lab-demo}。下面的小程序不需要 GPU；在工程目录用 \texttt{g++ -std=c++17 cpu\_demo.cpp -o /tmp/cpu\_demo} 编译，然后运行 \texttt{/tmp/cpu\_demo}。阈值为 0/255/0/255，前缀和为 1/8/10/18。观察哪一列只看本行输入、哪一列保留之前的状态。
\end{example}

\subsubsection{Thread、Block、Grid：每个线程处理哪一项}
CUDA 线程（thread）执行 kernel，通过内置索引区分工作；线程块（block）内可以共享数据和同步，网格（grid）包含这次启动的所有块。块分布到流多处理器（Streaming Multiprocessor，SM）执行，但一个 CUDA 线程不是一个物理核心，块的先后顺序也没有固定承诺。别用“第 0 块应该先算完”来设计块间通信。

一维索引为
\[
i=\texttt{blockIdx.x}\cdot\texttt{blockDim.x}+\texttt{threadIdx.x}.
\]
\texttt{threadIdx}、\texttt{blockIdx}、\texttt{blockDim}、\texttt{gridDim} 均可表示三维。启动通用形式是 \texttt{kernel<<<网格大小, 块大小>>>(参数)}，也可用 dim3 组织二维网格。图 \ref{fig:v2-cuda-grid} 用小数目画出索引，不让你从百万线程里找一根针。

\caption{三块中的全局索引，$t_0$ 等表示块内线程编号}\label{fig:v2-cuda-grid}

\subsubsection{共享内存与同步：让线程真正合作}
刚才每项都独立，共享内存还没派上用场。全局内存（global memory）容量大，设备数组通常放在这里；共享内存（shared memory）是块内的片上暂存，适合复用/合作；寄存器由线程私有使用，溢出等情况可能用到位于设备内存的 local memory。“local”说的是线程私有的访问范围，不等于一定很快。

现在求数组总和。每块先把本块数据放进 tile，超出长度的位置补 0，再两两合并；步长每轮减半，因此本实现限制块大小为二次幂。每轮写入结束都全块同步，下一轮才能读刚更新的值。块间没有这道屏障，所以各块先写一个 partial，下载后由 CPU 做最后汇总。

\subsubsection{错误检查：启动了，不代表算成了}
kernel 启动是异步提交，CPU 能继续向后执行。启动参数错误通常由 \texttt{cudaGetLastError()} 检查，执行期间的问题要在同步等操作处检查；它还可能报告此前的异步错误，所以需要保持每步检查，不能只在程序最后看一次。输出碰巧对了，也不能证明没有越界访问。

\begin{example}[区分两处错误]
先运行 launch：1025 超过本设备每块最多 1024，启动检查报告 invalid configuration argument，退出 1。再独立运行 execute：启动检查通过，设备断言在同步时报告 device-side assert triggered，退出 1。\texttt{\#undef NDEBUG} 只用于错误示例，防止 Release 配置把演示断言去掉。
\begin{tbash}
./build/error_demo launch
./build/error_demo execute
./build/vec_add 257 256
\end{tbash}
第三条在新进程正常通过。它说明这些演示错误没有被当成成功，也没有用继续操作坏上下文来“恢复”。
\end{example}
\begin{example}[工具检查实际访问]
Compute Sanitizer 的 memcheck 查访问问题，racecheck 查共享内存冲突，synccheck 查同步错误；一种工具通过不能代替另外一种。以下三条正常检查应报告 0 errors，最后一条故意越界应有 Invalid global write 报告及非零退出。通用形式为 \texttt{compute-sanitizer --tool 工具 [选项] 程序 [参数]}，\texttt{--error-exitcode 9} 让工具检测到错误时返回失败。
\begin{tbash}
compute-sanitizer --tool memcheck --error-exitcode 9 ./build/vec_add 257 256
compute-sanitizer --tool racecheck --error-exitcode 9 ./build/shared_sum 513 256
compute-sanitizer --tool synccheck --error-exitcode 9 ./build/shared_sum 513 256
compute-sanitizer --tool memcheck --error-exitcode 9 ./build/error_demo memory
\end{tbash}
本次越界报告同时包含非法写入与同步失败，返回 9；不能按“工具运行完了”算通过。具体工具范围见 \href{https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html}{官方检查工具文档}。
\end{example}
\begin{exercise}\label{ex:v2-cuda-error}
记录两个错误模式分别在哪个 API 被发现，并运行正常向量的 memcheck 与共享求和的 memcheck/racecheck/synccheck。保存退出状态和报告；说明零输出差异、启动检查和工具检查各自覆盖什么。
\end{exercise}

\begin{example}[比较同一程序的规模与传输]

\begin{tbash}
./build/pipeline

\end{tbash}

\begin{conclusion}
先保证同一输入与正确结果，再比较同一计时口径。预热与重复减少启动和偶然波动，事件需要等完成；主机时钟若不等待，只量到提交过程。减少传输可能比优化某个核更有效，实际工程还要计入采集、预处理、队列和后处理。
\end{conclusion}

\subsubsection{从算子接到推理部署*}
手写 kernel 适合学习机制和处理明确热点，常见视觉推理仍可先用成熟工具。上一章已经把真实 LeNet 导出 ONNX，再比较完整输出；ONNX 是交换计算图的形式，TensorRT 可在 NVIDIA 路径构建优化引擎，OpenVINO 则有自己的目标设备与运行栈。引擎的可移植范围取决于版本、构建选项和硬件，换平台要重新核对，不能只换后缀就叫部署完成。
\begin{example}[用完整开销判断优化价值]
假设上传 2 ms、三个算子合计 3 ms、下载 2 ms。每步各上传下载一次共 15 ms；统一上传下载一次为 7 ms。这是明确假设下的算术模型，实际程序用上一节 pipeline 观察。同样，一个 1 ms 算子减到 0.5 ms，在原来 5 ms 的完整路径里只减少 10\%，不能把局部“快一倍”说成整机快一倍。
\end{example}
\begin{exercise}\label{ex:v2-cuda-deploy}
按上述 2/3/2 ms 假设验证 15/7 ms 的构成，再用自己的 pipeline 记录指出实际路径还有哪些启动/同步成本。说明前章导出比较和本章计时分别提供了哪部分部署依据。
\end{exercise}
具体 TensorRT API 与引擎兼容性可查 \href{https://docs.nvidia.com/deeplearning/tensorrt/}{官方文档}，本章没有构建 TensorRT 引擎，不把文件能打开或 GPU 能访问写成加速部署完成。

\subsubsection{容器与无设备边界：缺哪一步就记哪一步}
最后回到你自己的机器。笔记本应先确认程序访问的是 NVIDIA 设备，容器/WSL 还需要对应透传；有 nvcc 但查询不到设备时先检查这些条件，别急着把正确的源码改坏。无 GPU 可独立构建 cpu\_demo、计算索引与字节数；CUDA 编译有时也能完成，但 GPU 执行、共享内存检查和计时仍需设备。
\begin{example}[模拟应用看不到设备]
以下环境变量只作用于这次 CUDA 进程，不移除物理显卡，也不证明容器真的没配好。device\_info 应报告没有可用 CUDA 设备并返回非零，本次由 cudaGetDeviceCount 报 no CUDA-capable device is detected、返回 1；CPU 小程序仍可运行，之后正常查询恢复原样。
\begin{tbash}
CUDA_VISIBLE_DEVICES='' ./build/device_info
CUDA_VISIBLE_DEVICES='' ./build/cpu_demo
./build/device_info
\end{tbash}
\end{example}

\end{exercise}
