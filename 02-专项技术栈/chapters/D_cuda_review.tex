\section{本章小结}
我们先把任务分成独立工作与有依赖的合作，再区分驱动、编译工具和运行库。完整工程串起主机输入、设备分配、上传、网格启动、同步、下载与 CPU 校验；索引和尾部条件决定每个线程是否有数据可处理。

共享归约需要补零、二次幂和逐轮块内同步，块间结果由主机汇总。提交成功不是执行成功，正常路径和预期报错都要观察；检查工具各有范围，不能相互替代。性能要从正确结果出发，区分核事件、包含传输的处理和实际相机端到端路径。推理引擎和更深入的优化可查对应文档，先保留能核对的基线。

\begin{problemset}
\item\label{prob:v2-cuda-dependency} 基础：逐像素阈值、朴素前缀和各依赖什么？CUDA 线程与物理核心是否一一对应，块能否依赖编号顺序执行？
\item\label{prob:v2-cuda-env} 基础：nvidia-smi、nvcc、PyTorch 构建与 runtime 查询分别说明哪一层？版本不同是否自动代表错误？
\item\label{prob:v2-cuda-memory} 基础：两个长度 512 的 float 输入与一个输出，设备数组、上传与下载分别需多少字节？如果主机也有三份数组，设备数组是否翻倍？
\item\label{prob:v2-cuda-index} 基础：n=513、每块 256 线程，块数、最后有效线程数和跳过数是多少？只检查首元素能证明没有越界吗？
\item\label{prob:v2-cuda-shared} 基础：Shared 与 local 的访问范围是什么？本归约为何补零、限制二次幂，屏障为什么在条件外？
\item\label{prob:v2-cuda-error} 基础：启动成功但设备断言时，哪个检查发现错误？memcheck/racecheck/synccheck 可以互相替代吗？
\item\label{prob:v2-cuda-timing} 提高：某次 kernel 事件为 0.01 ms、带传输路径为 0.8 ms，能够宣称相机单帧响应是 0.01 ms 吗？为什么主机计时前后需要明确等待？
\item\label{prob:v2-cuda-reduction} 提高：普通小数换成块归约后与 CPU 顺序求和略有差别，必然是线程错误吗？怎样同时检查同步和数值误差？
\item\label{prob:v2-cuda-practice} 实践：对检查者给出的非整块长度运行向量加法和共享求和，展示全部结果校验、访问/同步检查和完整流水线计时；说明环境、架构和缺失项。
\end{problemset}

\section{本章验收}
\begin{enumerate}
\item 从实际 Ubuntu 环境展示驱动、编译器、架构与 runtime，构建六个目标；说明包安装范围及旧 Driver 截图的适用条件。
\item 按现场长度/块大小算索引与字节数，运行向量加法并验证全部输出；再展示共享归约的 partial、总和与二次幂限制。
\item 展示正常 memcheck/racecheck/synccheck 和两个独立错误进程，定位启动、执行与访问错误；不把预期错误算作正常通过。
\item 报告 CPU、三核事件、留存和往返处理的计时与数据量，解释预热、同步、中位数和端到端边界；无 GPU 如实记录未完成运行项。
\end{enumerate}
