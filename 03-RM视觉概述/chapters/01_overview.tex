\subsubsection{两条技术路线如何在赛场结合}

前两卷带你装好了环境，也认识了不少算法。这时候你可能会问：东西学了这么多，上车时到底先用哪一个？我们先拿自瞄举个例子。相机拍到一张图，程序需要从里面找到装甲，算出它在哪里，再让云台跟过去。这里面既有图像处理，也有几何、滤波和控制，绝不是给网络喂一张图，后面的事就自动完成了。

找目标时，常用的办法可以分成两条路线。\textbf{传统图像处理（Traditional Image Processing）}从颜色、亮度、轮廓和几何关系入手，比如先把亮的区域筛出来，再找一对形状合适的灯条。你比较容易看清它为什么选中或放弃某个目标，不过曝光、背景和阈值变了，结果也可能跟着变。\textbf{深度学习（Deep Learning）}则让网络从数据中学习检测或分类。它能利用更复杂的特征，不过效果仍取决于训练数据和实际场景，部署时还要考虑输入尺寸、算力与耗时。不要先给两条路线排个强弱榜，能不能用，要放到你的场景里试。

赛场上我们经常把两者接起来：网络先给出候选框，传统方法在框内找角点，几何模块再根据标定和目标尺寸解算位置。传统方法也可以先找感兴趣区域（Region of Interest，ROI），缩小后续网络的搜索范围。细节分别回卷二的 OpenCV、深度学习与几何视觉章查；本章先把每一步传的东西认清楚。

\begin{example}[把网络与几何接起来]
准备一张纸，先画四个框：“图像 → 网络框 → 框内灯条角点 → 位姿”，然后在箭头旁标注数据类型。图像是像素阵列，框和角点是像素坐标，位姿则包含带坐标约定的旋转与平移。接下来检查最后一步还缺什么：相机标定、目标三维尺寸与角点对应关系。画到这里，你应当能指出为什么一个检测框本身不能直接当距离；也能看出网络与传统方法各负责哪一步。
\end{example}

\subsubsection{三个方向}

学工具时，你会听到识别、CUDA、激光雷达等名字；分配任务时，我们则按\textbf{最后要帮机器人做什么}来分。本书采用自瞄、雷达、导航三个方向，这是一种培训分工，不是比赛规则规定的三种岗位。

\textbf{自瞄}从车载图像中找到目标，估计和预测状态，为云台跟踪以及开火条件判断提供信息。\textbf{雷达}关注全场的目标位置与身份，把可用信息送到队内决策或允许的广播接口；RM 中的雷达站是比赛角色，不能只看名字就把它当成一台激光雷达。\textbf{导航}则回答“我在哪里、要去哪里、怎样过去”，移动平台上的定位、环境表达、规划与控制都在这条链路里，哨兵是常见应用对象。

这样分好以后，你会发现 GPU 加速可能同时用在自瞄和雷达里，激光雷达也可能参与导航或全场感知。器件和技能可以共用，方向还是要看输出服务于什么任务，不然大家都说自己在做“识别”，接口接给谁就说不清了。

\begin{example}[给需求分配方向]
把“跟随装甲转云台”“绕开障碍到补给点”“共享全场目标位置”写成三张卡，分别放到自瞄、导航、雷达栏。然后把“GPU 加速”放在三个栏下方，表示可以共同使用的工具。最后单独拿出“网络识别装甲”这张卡：它既可能为车载自瞄提供观测，也可能为雷达站提供身份信息，你还得追问它的输出交给谁。能说明这张卡为什么不能唯一归类，才算分清了任务与技术。
\end{example}

\begin{note}
不同赛制、赛季的机器人角色与通信许可会变化。需要确认上场功能时，先到 RoboMaster 官方\href{https://bbs.robomaster.com/wiki/20204847}{规则/资料中心}找到自己赛制、赛季的规则与协议，记录文件版本。本章的三个方向和后面的教学接口不替代规则文件，也不代表本队已经采用某项方案。
\end{note}

\subsubsection{视觉数据流（总览）}

现在我们从一条观测往后走。相机先产生图像，处理模块把它变成目标位置或状态，后面的模块再根据任务使用这些数据。图\ref{fig:v3-dataflow}画的是三类任务的关系，不是说三个方向共用一个估计节点，更不是所有传感器都要接到同一个进程里。

\begin{figure}[H]
\centering
\includegraphics[width=0.9\textwidth]{overview_dataflow_revised.pdf}
\caption{按输出职责区分三个方向；中间模块随任务选择，箭头不代表现行消息协议}
\label{fig:v3-dataflow}
\end{figure}

自瞄要把信息交给云台相关闭环，导航要把路径变成底盘能够执行的速度，雷达则把观测交给广播与辅助决策。后面的接收方能不能用，取决于前面有没有把单位、坐标系和时刻一起带过去。比如图像里的横坐标 320，既不是场地中的 320 米，也不是让云台转 320 度；数据类型都是一个数，物理含义可差得远了。

\begin{example}[追踪一条观测]
给纸面链路取一个帧号 42，再逐项写下：第 42 帧图像 → 像素角点 → 相机系目标位置 → 带时间戳的跟踪状态 → 云台目标角。每个箭头都写上数据名称和单位。走到空间位置时补上坐标系，走到状态时补上“状态属于哪个时刻”。最后故意把像素角点接到角度接口上，指出接收方缺少哪一步解释。这里检查的是字段的含义，不需要你先手推 PnP 或滤波器。
\end{example}

\begin{conclusion}
检测告诉你图里有什么，几何解算把图像量变成空间量，估计把多次观测组织成状态，控制与广播再使用状态。它们可以串起来，不能因为最后都存成数组就互换。读一条链路时，先追问每个箭头传什么，再追问数据属于哪个坐标系、哪个时刻。
\end{conclusion}

\subsubsection{与其它组别的接口边界}

算法跑起来以后，工作并不会只留在视觉组。首先，相机装在哪里、朝哪个方向、会不会抖，需要和机械一起确认。视觉提出视场（Field of View，FOV）、安装姿态和刚度需求，机械负责把结构做出来；安装角变了，视觉还得重新核对外参，不能只说“看着差不多”。然后，目标角和底盘速度需要电控接收并执行。视觉与电控要一起约定消息字段、坐标、时间和失效动作，执行器闭环如何分工也要写清楚。最后，雷达与导航给战术提供什么信息，需要和实际使用信息的人确认，发得出去不代表别人来得及用。

接口卡就是把这些约定记在一张能拿来核对的纸上。比如 yaw 是相对当前云台的增量，还是某个参考系下的绝对角？正号到底向左还是向右？失去目标以后继续沿用上一帧，还是停止更新？这些事先说清楚，比两边各写完以后对着乱转的云台猜原因省事。

\begin{example}[一张最小接口卡]
先写发送方视觉、接收方电控；然后把 yaw 定义为“相对当前云台的水平增量，左转为正，单位 rad”。再写采样时刻、有效标志、发送频率、协议版本和失效行为。尚未确认的频率与真实失效动作先标“待双方确认”，不要为了把表填满随便编一个数。让接收方解释 $+0.1$ 与 $-0.1$ 分别是什么动作，再拿相同输入核对。下面的程序会用同一张教学卡演示这件事，但不会连接实车。
\end{example}

项目位于本卷 \path{examples/interface-card-demo/}，只有 \texttt{card.json} 和 \texttt{receiver.py} 两个核心文件。卡片里的 \texttt{contract} 是双方约定，\texttt{message} 是一次观测；先看完整卡片，后面程序的检查就有了对应对象。

\texttt{demo\_clock} 是两端共用的教学时钟，采样在 20 ms，接收在 100 ms，所以数据年龄是 80 ms。100 ms 阈值只是本实验的设定，真实系统还要核对时钟同步和任务要求，不能把两台未同步机器的时间戳直接相减。\texttt{gimbal\_delta\_left\_positive} 则把“相对当前云台、左转为正”一起写进名字；工程里不一定这样命名，但物理定义不能省。

\begin{example}[让两端用同一条消息说话]
需要 Python 3.10 及以上，不用额外包。在卷三目录打开终端，先进入项目目录，再运行：
\begin{tbash}
cd examples/interface-card-demo
python3 receiver.py
python3 receiver.py --unit deg
python3 receiver.py --age-ms 101
python3 receiver.py --invalid
python3 receiver.py --delta -0.1
\end{tbash}
默认输出 \texttt{accept}，年龄 80 ms，角度约 $5.7296^\circ$。单位改成 deg 后输出 \texttt{hold / unit mismatch}；101 ms 已超过含边界的 100 ms 阈值；无效观测同样不接收。最后的负增量则解释为约 $-5.7296^\circ$。先预测每次会输出什么，再和终端比较，你就能分清“数值变了”与“数值含义变了”。
\end{example}

\begin{note}
\texttt{hold} 只是这个程序不再提供新角度，不代表实车已经停转。真实接收端还要处理解析失败、序号、丢包、限幅与看门狗，并由双方确认失效动作。上车前用队内版本化协议做联调，别拿这张教学卡当裁判协议或执行器安全方案。
\end{note}

\begin{conclusion}
相同字段名和存储类型，只能说明两边拿到了一样的字节，不能保证解释一样。接口变更要把消息定义、单位/坐标/时间、收发实现和验证样例一起同步；发现未确认项就写出来，口头说过并不能替仓库里的旧约定自动升级。
\end{conclusion}

\subsubsection{本卷读法}

我们把三卷分开，是为了让你遇到问题时能找到入口，不用从安装系统一直翻到最后。不会装环境、写 C++ 或使用 CMake，先回卷一；节点通信、PnP、滤波或控制的实现问题，到卷二找对应专项；不知道这些模块怎样接起来，或者调车时怎样留证据，就继续读本卷。开营可以先读第\ref{ch:v3-overview}、\ref{ch:v3-aim}、\ref{ch:v3-engineering}章，相机上机前再看第\ref{ch:v3-camera}章；基础过关后按方向补卷二，而不是把所有专项一口气背完才准动手。

\begin{example}[查找下一本书]
假设你已经能识别装甲，空间位置却一直跳。首先用本卷画出检测、解算、估计三段，然后在本地卷二找到 \path{chapters/E_camera.tex}、\path{chapters/G_ba.tex}、\path{chapters/F_filter.tex}，打开文件确认章内内容。记录你要查的是标定、角点对应，还是观测与状态的关系，再决定先看哪段。这样得到的是能继续检查的学习路径，不只是“去看算法”四个字。
\end{example}
