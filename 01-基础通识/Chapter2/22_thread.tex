
\subsubsection{基本概念}
多线程（multithreading）是指一个进程中同时运行多个线程（thread）。线程共享进程的地址空间，适合把互不依赖的工作拆开执行，例如同时接收相机数据、处理上一帧图像和保存日志。

多线程不等于程序一定更快。线程创建、调度和同步都有成本；如果多个线程频繁争抢同一份数据，程序反而可能变慢。因此，设计多线程程序时要先回答两个问题：哪些工作可以并行，哪些共享状态必须同步。

线程之间常见的协作方式有两类：
\begin{itemize}
    \item \textbf{阻塞等待}：线程暂时停下来等待事件，例如等待队列中出现任务，不会持续占用 CPU。
    \item \textbf{非阻塞尝试}：线程先尝试获取资源，失败后立即返回或执行其他工作。原子操作和 \texttt{try\_lock} 常用于这种场景。
\end{itemize}

如果多个线程同时读写同一对象，且至少有一个线程写入，却没有合适的同步，就会产生数据竞争（data race）。在 C++ 中，数据竞争会导致未定义行为，不仅仅是“结果偶尔不准”。

\begin{conclusion}
并发程序的基本思路可以概括为：独立的工作并行执行，共享的数据明确保护，线程的启动、等待和退出形成完整闭环。后文将依次介绍互斥锁、共享锁、原子变量、条件变量和异步结果传递。
\end{conclusion}

\subsubsection{互斥锁与 RAII 锁}
当多个线程修改同一份共享数据时，需要把“读—改—写”的完整过程保护起来。\texttt{std::mutex}（互斥量，mutex）保证同一时刻只有一个线程进入临界区。

下面的自增操作看起来只有一行，实际上包含读取、计算和写回三个步骤。两个线程可能读到同一个旧值，造成更新丢失。

\texttt{std::lock\_guard} 是 RAII\footnote{
    RAII 是 Resource Acquisition Is Initialization 的缩写，意为“资源获取即初始化”，是一种 C++ 编程习惯。它的核心思想是：把资源的获取和释放绑定到对象的生命周期上，构造时获取资源，析构时释放资源，从而避免忘记释放资源或异常导致的泄漏。
}锁。构造时加锁，离开作用域时自动解锁，即使临界区中途抛出异常也能释放锁。需要手动解锁、延迟加锁或转移锁所有权时，可以使用 \texttt{std::unique\_lock}。

\begin{tcode}
std::unique_lock<std::mutex> lock(mtx);  // 默认立即加锁
lock.unlock();                           // 可以提前解锁
lock.lock();                             // 也可以再次加锁
\end{tcode}

\begin{note}
不要把共享数据的读操作放在锁外、写操作放在锁内，除非你能证明这样做是安全的。锁保护的不是某一行代码，而是一个必须保持一致性的临界区。
\end{note}

\subsubsection{共享锁与相容性矩阵}
在读多写少的场景中，多个线程同时读取通常不会互相破坏数据。如果所有读者都使用普通互斥锁，读者之间也会被迫排队。\texttt{std::shared\_mutex} 提供两种锁模式：\texttt{std::shared\_lock} 是共享读锁，允许多个读者同时持有；\texttt{std::unique\_lock} 是独占写锁，写入时阻塞所有读者和其他写者。

两种锁的相容性可以用下面的矩阵记忆。行表示当前已经持有的锁，列表示申请的新锁。

\begin{center}
\begin{tabular}{c|cc}
\toprule[1.5pt]
当前持有的锁 / 新申请的锁 & 共享读锁 & 独占写锁 \\
\midrule[1pt]
共享读锁 & 相容 & 冲突 \\
独占写锁 & 冲突 & 冲突 \\
\bottomrule[1.5pt]
\end{tabular}
\end{center}

多个读者可以并行读取；只要有一个写者进入，其他读者和写者都必须等待。共享锁只能保护“读操作确实不会修改数据”的代码。

\begin{conclusion}
普通互斥锁、共享读锁和独占写锁的选择：
\begin{itemize}
    \item 数据会被修改，或读写逻辑无法清楚区分：使用普通互斥锁。
    \item 读操作远多于写操作，且读操作不会修改数据：考虑 \texttt{shared\_mutex}。
    \item 读锁之间相容，写锁与任何锁都冲突；写入必须使用独占锁。
\end{itemize}
\end{conclusion}

\subsubsection{原子变量}
原子变量（atomic variable）适合表示一个简单的共享状态，例如计数器、标志位或索引。\texttt{std::atomic<T>} 保证对该对象的单次读写或指定的原子操作不会被其他线程看到“做到一半”的状态。

原子变量不是“万能同步工具”。两个原子变量之间的联合不变量\footnote{联合不变量是指多个变量之间需要共同满足的条件，例如两个变量的和始终保持为10}仍可能被其他线程观察到中间状态；一组复杂数据结构也不能仅靠把某个整数改成原子类型来保护。

从本卷目录进入 \path{examples/thread-coordination-demo}，源码保存在 \texttt{atomic.cpp}。
\begin{tbash}
g++ -std=c++17 -Wall -Wextra -pthread atomic.cpp -o /tmp/cpp-demo
/tmp/cpp-demo
\end{tbash}
看到停止提示与 counter = 200000；yield 是轮询让步，表示向调度器请求让出 CPU。
\end{example}

常用操作包括 \texttt{load()}、\texttt{store()}、\texttt{fetch\_add()} 和 \texttt{exchange()}。直接使用自增运算符也可以执行原子自增。若需要多个共享对象保持整体一致，应回到互斥锁或更高层的并发结构。

\begin{note}
不要用普通的 \texttt{bool} 作为多个线程共享的停止标志，也不要用“先读取再判断再写回”的普通变量操作代替原子操作。数据竞争属于未定义行为，不能依靠多运行几次没有出错来证明程序正确。
\end{note}

\subsubsection{条件变量}
条件变量（condition variable）解决的问题是：线程需要等待某个共享状态成立，但又不应该一直轮询占用 CPU。例如，消费者要等待队列非空，工作线程要等待“停止”或“有新任务”。

条件变量必须和互斥锁、共享状态一起使用。等待流程是：先获得锁，调用带谓词\footnote{谓词是返回布尔值的函数或 lambda 表达式}的 \texttt{wait}；被唤醒后重新检查谓词，条件满足才继续执行。

\begin{tcode}
std::condition_variable cv;
std::mutex mtx;
bool ready = false;
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [] { return ready; });
}
cv.notify_one();       // 唤醒一个等待线程
cv.notify_all();       // 唤醒所有等待线程
\end{tcode}

\texttt{wait} 在等待期间会暂时释放互斥锁，被唤醒后重新加锁再返回。必须使用谓词版本，因为可能出现虚假唤醒\footnote{条件没满足进程却醒来}，而且其他线程被唤醒后可能已经先一步改变了共享状态。

\begin{conclusion}
原子变量和条件变量解决的是两类不同的问题：原子变量适合完成一个简单状态的无竞争读写；条件变量适合让线程在\textbf{某个受锁保护的条件}不成立时休眠等待。原子变量不会自动把线程挂起，条件变量也不能代替锁来保护复杂数据。
\end{conclusion}

\subsubsection{future、promise 与 async}

\subsubsection{线程池：组合前面的工具}
线程池（thread pool）预先创建一组工作线程，用任务队列复用它们。它可以减少频繁创建和销毁线程的开销，也能限制同时运行的任务数量。调用方提交任务，空闲的工作线程从队列中取出任务执行；这正好把互斥锁、条件变量和线程生命周期管理组合到了一起。

实现线程池时至少要处理三件事：任务队列的互斥、空队列时的等待、析构时的停止与唤醒。工作线程取出任务后应先释放队列锁，再执行任务，避免一个慢任务阻塞其他线程提交或取任务。

\Needspace{9\baselineskip}
\begin{example}
一个可正常停止的简易线程池：
\lstinputlisting[language=C++,numbers=left,numberstyle={\color{gray}\tiny}]{examples/thread-coordination-demo/pool.cpp}


从本卷目录进入 \path{examples/thread-coordination-demo}，源码保存在 \texttt{pool.cpp}。

\subsubsection{并发进阶：经典问题}
前面的互斥锁、条件变量和共享锁是零件；下面四个问题带我们练习的是“看到场景后，知道该拿哪块零件”。先不要急着记解法。每个问题都先回答三件事：\textbf{谁在同时做事}、\textbf{谁在共享什么}、\textbf{不协调会发生什么}。视觉工程里的帧队列、参数表和设备资源竞争，都能在这里找到原型。

\textbf{生产者—消费者问题。}
想象相机线程不断产生图像帧，识别线程不断取帧处理。前者是\textbf{生产者}，后者是\textbf{消费者}，两者之间只有一个容量为 3 的帧队列。它们共享的是队列，而不是“某一帧图像”。

这个问题要保证三件事：每个放入的任务只取出一次；队列不能超过容量；队列空时消费者不能取一个不存在的任务，队列满时生产者也不能继续塞。若用循环反复检查队列，会白白占用 CPU；因此队列空或满时，对应线程应该睡眠，状态变化后再被唤醒。生产者把数据放入有限容量的缓冲区，消费者从缓冲区取出数据；这正是条件变量最典型的使用场景。

\textbf{读者—写者问题。}
想象多个线程都要读取一份曝光参数表，只有调参线程偶尔会修改它。读参数的线程是\textbf{读者}，修改参数的线程是\textbf{写者}，共享资源是这份参数表。两个读者同时看到同一份稳定的参数没有问题；但写者写到一半时，任何读者都不能读，两个写者也不能同时写。

这个问题关心的不只是“正确”，还关心“效率”：若所有人都用普通互斥锁，读者之间也只能排队，读多写少时就浪费了并行机会。因此读者可以并行，写者必须独占。还要留意公平性：如果系统总让新读者先进入，写者可能长期得不到机会，这叫写者饥饿。\texttt{std::shared\_mutex} 能表达基本的读写互斥关系，公平性则要根据具体需求额外设计。

\Needspace{9\baselineskip}
\begin{example}
多个读者共享读取、写者独占更新：
\lstinputlisting[language=C++,numbers=left,numberstyle={\color{gray}\tiny}]{examples/thread-coordination-demo/readers-writers.cpp}


仍在本节项目目录中，编译并运行 \texttt{readers-writers.cpp}：
\begin{tbash}
g++ -std=c++17 -Wall -Wextra -pthread readers-writers.cpp -o /tmp/cpp-demo
/tmp/cpp-demo
\end{tbash}
每个读者读到 0 或 100，读取有共享锁，更新有独占锁；谁先执行由调度决定。
\end{example}

\textbf{哲学家进餐问题。}
这是一个把“多个任务同时申请多份资源”放大的小故事。五位哲学家各是一条线程，五把叉子各是一份只能被一个人使用的资源。第 $i$ 位哲学家只有同时拿到左、右两把叉子才能吃饭；而每把叉子又与相邻哲学家共用。

麻烦出在“先拿到一份资源，再等另一份资源”。若每个人都先拿左叉子，就可能五个人各拿一把叉子，再一起等右边那把；谁也不能继续。真实工程中的“同时锁住相机和串口”“同时更新两个关联缓存”也是同一种结构。

一种简单的规避办法是打破对称性；更通用的办法是使用 \texttt{std::scoped\_lock} 采用避免死锁的算法共同管理两把锁，不让各线程永久持有一把又等另一把；这不等于一次硬件原子操作拿齐锁，也不保证公平性。

\Needspace{9\baselineskip}
\begin{example}
使用 \texttt{scoped\_lock} 安全获取两把叉子：
\lstinputlisting[language=C++,numbers=left,numberstyle={\color{gray}\tiny}]{examples/thread-coordination-demo/philosophers.cpp}


从本卷目录进入 \path{examples/thread-coordination-demo}，源码保存在 \texttt{philosophers.cpp}。
\begin{tbash}
g++ -std=c++17 -Wall -Wextra -pthread philosophers.cpp -o /tmp/cpp-demo
/tmp/cpp-demo
\end{tbash}
每位哲学家吃两次后所有线程退出，输出可能交错；共同获取两锁避免这一组资源的循环等待。
\end{example}

\textbf{死锁。}
死锁（deadlock）不是“程序运行得慢”，而是线程组成了一个谁也无法先让步的等待圈。比如线程 A 拿着资源 1 等资源 2，线程 B 拿着资源 2 等资源 1；资源 2 只有 B 释放后 A 才能得到，资源 1 也只有 A 释放后 B 才能得到。两条线程都不会自动恢复，程序就停在这里。哲学家进餐问题正是死锁可能出现的一种场景。

上面的等待圈并非偶然。死锁发生时会同时满足以下四个必要条件：
\begin{enumerate}
    \item \textbf{互斥}：资源同一时刻只能被一个线程占用；
    \item \textbf{持有并等待}：线程已经持有资源，同时等待其他资源；
    \item \textbf{不可抢占}：资源不能被强行从持有者手中夺走；
    \item \textbf{循环等待}：线程之间形成首尾相接的等待环。
\end{enumerate}

只要破坏其中一个条件，就能避免死锁。工程中最常用的做法是给资源规定全局获取顺序；需要同时获取多把锁时使用 \texttt{std::lock} 或 \texttt{std::scoped\_lock}；还可以设置超时，让等待失败后回滚。

\Needspace{9\baselineskip}
\begin{example}
两个线程以相反顺序获取两把锁，会形成循环等待：
\lstinputlisting[language=C++,numbers=left,numberstyle={\color{gray}\tiny}]{examples/thread-coordination-demo/deadlock.cpp}


从本卷目录进入 \path{examples/thread-coordination-demo}，源码保存在 \texttt{deadlock.cpp}。
\begin{tbash}
g++ -std=c++17 -Wall -Wextra -pthread deadlock.cpp -o /tmp/cpp-demo
timeout 2s /tmp/cpp-demo
\end{tbash}
可能正常退出，也可能被 timeout 以状态 124 停止。
\end{example}

这是可能死锁的错误示范：线程一持有 \texttt{first} 等待 \texttt{second}，线程二持有 \texttt{second} 等待 \texttt{first}。下面改用 \texttt{std::scoped\_lock}，由标准库执行避免死锁的多锁获取算法。

\begin{tcode}
void safe_update() {
    std::scoped_lock lock(first, second);
    // 同时安全地访问由 first 和 second 保护的数据
}
\end{tcode}

\begin{note}
“把锁的作用域写得更小”可以降低竞争，但不能自动消除死锁。只要多个线程以不同顺序获取多把锁，死锁风险仍然存在。请在接口设计阶段统一资源顺序，避免让调用者随意嵌套加锁。
\end{note}

经典问题对应的解决工具：
\begin{center}
\begin{tabular}{p{2.7cm}p{3.5cm}p{5.5cm}}
\toprule[1.5pt]
问题 & 共享状态 & 主要思路 \\
\midrule[1pt]
生产者—消费者 & 有限容量队列 & 互斥锁保护队列，条件变量等待非空或非满 \\
读者—写者 & 读多写少的数据 & 读者共享、写者独占，关注公平性 \\

\bottomrule[1.5pt]
\end{tabular}
\end{center}
\end{conclusion}
