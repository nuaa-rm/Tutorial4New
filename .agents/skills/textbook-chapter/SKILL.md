# 教材章节编写与改造规范

读者是零基础或基础薄弱的本科新生。写作目标：让读者能照着教材独立完成任务，并通过练习确认自己学会了。语言使用简体中文，代码注释也用简体中文，术语首次出现给中英文对照。

## 适用原则

以读者能看懂、能动手、能验证为判断标准。章节的核心教学结构和检查清单是验收要求，修订时必须逐项检查，缺失必须补齐。题量、篇幅、排版参数及文件组织可以按实际需要调整，但不能借此省略核心示例、练习、总结、验收或验证。检查覆盖完整章节，不要求每个被引入的 `.tex` 子文件重复章首、章末结构。

默认实现方式妨碍讲解、组织或编译时，可以采用效果相当或更好的替代方式，说明理由及其对应的要求，不能只写“按需简化”就跳过检查。修订教材时不得通过自行降低验收标准来掩盖未完成项。用户明确提出的要求优先。

## 章节结构与要求

### 1. 章首：内容提要

完整教学章节的章首必须有 `introduction`，交代学习目标、建议学时和本卷边界。通常放在 `\chapter{...}` 之后；条目可以合并或增补，但这三项信息不能缺失：

```latex
\begin{introduction}
  \item 学习目标：……（用可验证的行为动词，如"编写""完成"，避免"了解""理解"）
  \item 建议学时：……
  \item 本卷边界：……（说明本章不讲什么、指向哪一卷）
\end{introduction}
```

### 2. 小节正文：讲解 → 示例 → 练习

1. **概念讲解**：先讲"做什么、为什么"，再讲"怎么做"。命令或语法类内容通常先给通用形式（如 `free [options]`），再按需要解释参数；参数较少时直接在正文说明，不必为了结构单独列一张表。通用语法和具体调用示例要区分清楚。
2. **示例**：每个核心小节必须有完整可运行或可照着操作的示例，默认用 `example` 环境包裹。连续界面教程可以用连贯的步骤与截图作为等效操作示例，但必须交代前提、操作和结果判断。相关小节可以共用一个完整示例，前提是逐个说明它覆盖哪些知识点，不能只因附近出现过一段代码就认定已满足要求：

```latex
\begin{example}
统计当前目录下各子目录的磁盘占用，并按易读单位显示：
\begin{tbash}
du -h --max-depth=1 .
\end{tbash}
\end{example}
```

3. **随堂练习**：每个核心小节必须有与刚讲内容紧密相关的 `exercise`，默认 1~2 道、5~15 分钟可完成。相邻小节可以合并成综合练习，但每个核心能力都要有明确的练习任务，不能用一句“自行尝试”代替。题量和位置可以调整，知识点覆盖不能省略：

```latex
\begin{exercise}
使用 find 在家目录下查找所有 7 天内修改过的 \texttt{.py} 文件。
\end{exercise}
```

### 3. 困难知识点：阶段性小结（按需）

符合以下任一条件的知识点必须有阶段性小结，默认使用 `conclusion`。附近已有明确对应的总结或对比表时可以复用，注明对应位置，避免重复；不能仅以“正文已经讲过”为由省略归纳：
- 涉及多个易混淆概念（如硬链接 vs 软链接、值传递 vs 引用传递）；
- 初学者常见错误已知（如 `rm -rf` 误用、迭代器失效）；
- 知识点跨多个小节才讲完。

小结通常使用 `conclusion` 环境，可用简短段落、对比表格或要点列表，篇幅以帮助读者归纳而不重复正文为准：

```latex
\begin{conclusion}
硬链接与软链接的区别：……（表格或 3~5 条要点）
\end{conclusion}
```

易错点和注意事项用 `note` 环境随时插入正文，不必等到小结：

```latex
\begin{note}
\texttt{rm -f} 不会询问确认，脚本中使用时务必先检查变量是否为空。
\end{note}
```

### 4. 章末：小结、习题与验收

完整教学章节必须有本章小结、章末习题和本章验收，默认按以下顺序组织。可以调整顺序或删去重复解释，但三者的功能和可定位内容都要保留。短章、选读章可以减少篇幅和题量，不能仅因篇幅短或属于选读就省略这些要素；章内短小子节不必重复整章结构。

```latex
\section{本章小结}
% 用 conclusion 环境或要点列表回顾全章知识地图：学了什么、各部分如何串联、
% 哪些是必须熟练掌握的、哪些只需知道去哪查。通常控制在 1 页左右。

\begin{problemset}   % 自动排版为"第X章 练习"，带目录条目
\item （基础题，覆盖每个核心小节至少 1 题）
\item （提高题，需要组合多个知识点）
\item （实践题，需在真实环境完成并验证结果）
\end{problemset}

\section{本章验收}
\begin{enumerate}
    \item ……（保留现有的验收清单风格：可检查、可演示的操作性任务）
\end{enumerate}
```

- `problemset` 与"本章验收"的分工：**习题**用于自测知识点（有标准答案），**验收**用于考核操作能力（由学长检查）。两者不重复出题。
- 习题量：全章 5~10 题可作参考，以核心能力覆盖和练习价值为准，不按小节数机械凑题，避免随堂练习和章末习题仅换个说法重复。

### 5. 参考答案

所有随堂练习和章末习题必须有对应参考答案；开放实践题必须给出验收标准或一种可行思路。题解与题目分开，沿用所在卷已有的 `answers.tex`、`answer.tex` 或独立题解结构，保证题目与答案能够互相定位，不因文件名不同新建重复的答案文件。

## 复杂概念的小项目演示

对于仅靠文字或零散代码难以讲清、需要观察代码执行过程或多个文件协作才能理解的复杂概念，必须用精简的小项目演示，并把项目讲解放在对应知识点附近。

1. **项目放在对应卷内**：在该卷的 `examples/` 下创建名称能体现概念的项目目录，例如 `examples/<概念名>-demo/`。已有项目能够承担演示时优先复用或精简，不重复创建同类示例。正文写明项目相对于该卷的路径。
2. **精简但完整可运行**：一个项目集中讲清一个核心概念，只保留必要的源码、配置、构建文件和少量演示数据，不引入与教学目标无关的框架或功能。不能用伪代码、缺失的文件或未交代的依赖代替可运行项目；需要输入数据时，提供小样本或生成方法。
3. **提供最短运行说明**：项目内的 `README.md` 写清演示目的、必要依赖、从哪个目录执行构建和运行命令，以及应观察到的输出或现象。示例优先使用能稳定复现的小规模输入，让读者把运行结果与概念对应起来。
4. **正文展示项目内容并讲清作用**：先说明项目要解决什么问题、演示什么概念，再展示精简的目录结构、用于解释概念的完整核心代码和影响行为的关键配置，使用现有代码环境排版。按执行顺序解释各文件或代码块的作用、它们如何配合，以及关键语句为什么这样写；随后给出构建运行命令、预期结果及其对应的概念结论。不能只给项目路径或让读者自行阅读源码。正文代码应与项目实际文件一致，能直接引入源文件时优先引入，手工摘录时同步维护。
5. **必要时用图片辅助理解**：当数据流、模块关系、状态变化或运行效果难以靠代码直接看懂时，加入流程图、关系图、前后对比图或真实运行截图，并在正文说明读者应该看哪里、图中现象如何对应代码。配图遵守图片风格与整理标记规则，不能用图片代替必要的代码讲解。
6. **验证演示是否讲得通**：实际按给出的命令构建并运行，检查结果是否支持正文结论；有助于理解时，再演示修改一个关键参数或语句后的变化，并解释原因。若依赖硬件或当前环境无法运行，明确说明已完成的检查和未验证的部分，不把预期结果写成实测结果。

## 模板环境速查

| 用途 | 环境 | 是否带编号 | 说明 |
|---|---|---|---|
| 章首提要 | `introduction` | 否 | 双栏条目，只放 `\item` |
| 例题 | `example` | 是（章内编号） | 显示名为"示例"，标题可后接 `[自定义说明]` |
| 随堂练习 | `exercise` | 是 | 同上 |
| 章末习题 | `problemset` | 列表内编号 | 内部直接写 `\item` |
| 注意/易错 | `note` | 否 | 带警示图标 |
| 小结 | `conclusion` | 否 | 蓝色标题块 |
| 补充说明 | `remark` | 否 | 简短评注 |
| 参考答案 | `solution` | 否 | 可被全局隐藏 |
| C++ 代码 | `tcode` 或 `tcpp` | 行号 | 带边框、语法高亮 |
| Python 代码 | `tpython` | 行号 | 同上 |
| Shell 命令 | `tbash` | 行号 | 同上 |

其他约定：
- 正文层级：先检查所在卷的 `main.tex` 和共享 preamble 的实际层级映射，按文件承担的层级使用标题命令。普通正文子文件通常从 `\subsubsection` 写起，章末或其他承担节级结构的文件可以使用 `\section`；不把某种子文件的惯例套到所有文件上。必要时整理标题命令或映射，使目录和编号正确。
- 表格通常使用 `booktabs` 三线表，线宽和布局与相邻正文协调；表头按实际比较内容命名，不固定为命令参数表。
- 图片通常使用 `figure` 环境，宽度 `0.7~0.9\textwidth` 可作起点，按清晰度和版面调整。需要紧跟步骤时可用 `[H]`，其他情况允许合理浮动，避免大块空白。独立教学插图应有图注；正文需要交叉引用的图片应有唯一标签。
- 代码内转义字符为反引号 `` ` ``（`escapechar=` ` ``），LaTeX 命令可借此嵌入代码。

## 写作风格

1. 面向初学者：每个命令/语法第一次出现时，先说清楚"它解决什么问题"。
2. 通常先通用语法、后必要参数说明、再具体示例；也可以先展示一个能解决眼前问题的调用，再归纳语法，但要让读者分清哪些是固定写法、哪些可以替换。
3. 篇幅克制：参数只讲当前任务和常见场景需要的部分，较多时用表格，按需指向 man 手册或官方文档，不限定条目数。
4. 危险操作（`rm -f`、分区、格式化等）应在操作前明确提示影响及必要准备，通常用 `note` 突出；紧邻步骤的醒目提示也可以，不能为了轻松口吻淡化风险。
5. 推荐外部资源（文档、练习网站）放在相关讲解或 `note` 中，用 `\url{}` 或 `\href{}` 给出链接，说明它能帮助解决什么问题。
6. 不重复：同一知识点只在一个小节展开，其他处用"见 X 节"引用（DRY）。

## 语言口吻

1. **简洁直白**：用词日常，避免学术腔和难读的长定语从句。以自然连贯、让初学者一遍看懂为标准，不强行拆成短句。多用第二人称与读者拉近距离。
2. **可以风趣**：允许在讲解、示例和习题中适当开玩笑、用梗（包括二次元梗），让读者感到教材是"学长写的"而不是"标准文档抄的"。例如：
   - 讲 `rm -rf` 时："这条命令删库跑路一气呵成，使用前请三思——你的存档没有读档功能。"
   - 讲 git 合并时："分支 A 和分支 B 表示：我们联合！"
   - 讲"一切皆文件"时："你以为是 U 盘设备？其实是我文件哒！"
   - 讲 vim 退出时："江湖传言，让新手自己尝试退出 vim 是一种可靠的随机字符串生成方式。"
   - 示例文件名、习题情景可以用读者熟悉的游戏/动漫元素。
3. **浓度放宽但有底线**：梗是调味料不是主菜——
   - 通常放在过渡、提醒、总结或习题情景中；帮助理解的类比也可以融入正文。不限定出现位置，但技术术语、参数含义、命令和代码注释应保持清楚可检索，不能靠玩梗代替解释；
   - 不设每小节/全章数量硬上限，以"读着不累、像学长在聊天"为度；同一个小节里梗不要扎堆，讲透一个再放下一个；
   - 梗要通用易懂，不依赖冷门作品；不用任何可能冒犯读者的梗；
   - 危险操作警示（`rm -f`、格式化等）可以幽默但警示信息本身必须清晰无歧义。
4. 口吻统一为"学长带学弟"：平等、鼓励、偶尔吐槽，不说教、不端着。

### 作者语言风格的具体表达习惯

编写和修订正文时遵循以下表达习惯，使整篇文章像有人坐在旁边带着读者一步步操作，而不只是给出一份操作清单：

1. **从读者当前的处境接着讲**：开头先承接刚完成的事情，或提出接下来很可能遇到的实际问题，再说明为什么要学这一节。动机落在具体后果和用途上，不用空泛的背景介绍或意义拔高。
2. **用“你”指向操作，用“我们”带着推进**：描述读者自己的机器、文件和选择时用“你”；一起分析原因或进入下一步时自然用“我们”。阶段完成时可以简短鼓励，遇到问题时先接住读者的疑惑，再解释怎么处理，避免居高临下地评价新手。
3. **保留连贯的讲解段落**：用“首先”“然后”“这时候”“接下来”“不过”“如果”等衔接动作、原因和分支，按读者实际动手的顺序推进。写清在哪里操作、选择什么、随后会看到什么、怎样判断完成。简洁是删掉废话，不是把每句话都截成短句；连续步骤可以在段落中自然串起来，只有需要比较或逐项核对时才用列表和表格。
4. **随操作解释原因，提前回答容易卡住的地方**：不只给出命令或按钮，还解释为什么这样选、参数对应什么、哪些名字和路径要换成自己的。出现报错或界面差异时，按“看到的现象 → 原因或适用条件 → 处理方法”说明；安抚要有依据，不能笼统保证报错都可以忽略或操作一定没风险。
5. **用具体类比把机制讲明白**：可以借助拍照、存档、回档、日常物品或简单的前后状态例子，把抽象概念变成能想象的过程，然后落回真实机制，说明类比的边界。帮助理解的类比可以进入知识点讲解；纯娱乐性的梗仍遵守上面的使用范围，不能代替解释或改变技术含义。
6. **给出推荐，也留出选择余地**：有多种方法时，先交代适合多数初学者的一种及理由，再说明什么情况下需要另一种。可以用自然的条件句说明哪些步骤可跳过、哪些内容按需学习，以及省事方案的代价，不把所有进阶配置都写成必须完成。个人偏好可以直说，但不能虚构作者经历或把偏好当成普遍结论。
7. **轻松感来自顺口的表达和贴近场景的吐槽**：可少量使用口语、括号补充、反问或语气词，让提醒和过渡有温度；不要每段都塞梗、强行套流行语或靠连续感叹号制造语气。关键步骤和危险操作先把要求、后果与补救办法说清楚，再考虑幽默。模仿的是讲解方式，不沿用原文中的错别字、单位混用或不准确的技术结论。

## 图片风格与整理标记

- 修订章节时，也要实际查看正文引用的图片，并结合所在段落和相邻插图检查风格是否统一：配色、字体与字号、线条与箭头、图内术语和语言、信息密度与表达方式应与文章风格协调，适合初学者阅读。不能只检查文件名、图注或图片是否存在。
- 风格不统一的图片必须修改或重绘，保留原有技术含义、数据和必要标注；真实截图中的命令、输出和界面信息不得为了统一外观而篡改。修改后在正文实际排版尺寸下检查清晰度、风格和图文对应关系。
- 图片修改并检查通过后，在扩展名前统一加 `_revised` 标记，例如 `ros_graph.png` → `ros_graph_revised.png`；再次修改时沿用该标记，不重复追加。只改名、尚未完成检查的图片不能标记为已整理。
- 改名后同步更新所有引用该图片的 `\includegraphics` 路径及相关生成脚本中的输出路径，确保正文使用整理后的图片且编译无缺图。
- 后续修订默认跳过带 `_revised` 标记的图片，避免重复查看和整理；若正文风格或技术内容变化、图片重新生成，或发现图文不符、显示异常，则重新检查，确认通过后继续保留标记。

## LaTeX 文件命名、引用结构与格式整理

修订时也要检查所涉及的 LaTeX 文件及其关联引用。混乱已经影响阅读、定位、维护或编译时，应一并整理；既有写法虽不完全一致但含义清楚、运作正常时，不必只为形式一致批量改动。“最小侵入”用于控制无关改动，不能阻碍解决实际问题；必要时可以重排小节或调整拆分方式，保留技术含义并让学习顺序更清楚。

1. **文件命名便于辨认**：优先使用能体现主题和用途、与所在卷习惯协调的名称。编号或缩写在目录及主文件中含义清楚时可以保留；确实难以定位、与内容不符或容易混淆的名称应重命名，不因文件名缺少主题词就自动判定需要修改。
2. **理清文件组织与包含关系**：梳理从 `main.tex` 到章节、子文件的 `\input`、`\include` 等关系，让入口、层级和阅读顺序清楚。整理散乱目录、重复包含、循环包含、失效路径，以及职责不清的拆分或嵌套；必要时移动、合并或拆分文件，避免同一段正文重复维护。整理前先查清全部调用方，改名或移动后同步更新主文件、其他卷、构建脚本和相关文档中的引用路径，保持图片和示例源码路径可用。
3. **规范交叉引用**：检查 `\label`、`\ref`、`\pageref` 等标签与引用是否匹配、唯一且含义明确，修复重复标签、未定义引用和指向错误的位置。新增标签按用途清楚命名，已有有效标签无需仅为统一前缀全部改写。章节、图表和公式编号可能变化时优先用标签引用；涉及文献时也检查 `\cite` 与文献条目的对应关系。修改标签时同步更新所有引用。
4. **统一源码与排版格式**：整理影响可读性或版面的缩进、空行、环境嵌套、标题层级，以及列表、表格、图注、代码块和强调方式，优先沿用项目模板与相邻正文的合理写法。保持代码、命令、路径、公式、逐字环境和有语义的 `%`、换行等内容不被机械格式化破坏；局部排版调整应有明确用途，避免堆叠临时补丁掩盖结构问题。
5. **验证整理结果**：整理完成后，从对应卷的主文件按项目构建方式编译，按需完成文献构建并运行至引用和编号稳定；不必每改一个文件就重编整卷。确认没有缺失文件、重复标签、未定义引用或影响阅读的排版问题，检查 PDF 中受影响的目录、顺序、编号、图表与代码。修改共享模板或映射时检查受影响的其他卷。环境无法完成编译时如实说明已检查和未验证的部分。

## 改造现有章节检查清单

对修订涉及的完整章节逐项检查。每项记录“通过 / 不适用 / 未完成”及对应的文件位置或验证依据；缺失项必须补齐后才能记为通过。只有不存在该项检查对象时才能记为“不适用”（例如本章没有图片）；采用等效实现时仍需说明覆盖依据，不能记为“不适用”。缺少运行环境、硬件或资料导致无法确认的项目记为“未完成”，说明已做的检查与缺口，不得当作已通过。必要时调整顺序、文件组织或模板，但不能减少验收覆盖。

- [ ] 章首存在 `introduction`，学习目标、建议学时、本卷边界三项信息齐全，目标可验证。
- [ ] 每个核心小节都有 `example` 或明确的等效操作示例，前提、完整代码或操作步骤、结果判断齐全；共用示例时覆盖关系清楚。
- [ ] 需要代码才能讲清的复杂概念在对应卷的 `examples/` 中有精简、完整可运行的小项目，包含必要文件、依赖和运行说明。
- [ ] 正文展示小项目的结构、完整核心代码和关键配置，解释作用与协作过程，给出运行命令和结果解读；内容与项目文件一致，必要的辅助图已补齐。
- [ ] 命令有通用语法、必要参数解释和具体调用示例，可替换的路径、参数及环境条件说明清楚。
- [ ] 每个核心小节有 `exercise`，默认 1~2 道；合并练习或调整题量时说明覆盖关系，每个核心能力都有具体任务。
- [ ] 易混淆概念、已知难点和跨节知识有 `conclusion` 或明确对应的归纳、对比表，不用重复正文代替总结。
- [ ] 已知易错点有明确说明；危险操作在动手前有醒目警示，影响和必要准备清楚。
- [ ] 存在“本章小结”，能呈现知识地图、知识之间的联系及掌握重点。
- [ ] 存在 `problemset`，默认全章 5~10 题，包含基础、提高与实践任务并覆盖核心知识；调整数量或题型时说明教学依据，不能漏掉自测。
- [ ] 存在“本章验收”，要求是可检查、可演示的操作能力，且与习题分工清楚。
- [ ] 所有随堂练习和章末习题有可定位的参考答案，开放题有判断标准或可行思路，题目与答案对应无遗漏。
- [ ] 正文符合作者语言习惯：承接实际场景、自然带着操作、随步骤解释原因，段落连贯，轻松表达不影响技术准确性。
- [ ] 未标记图片已实际查看并检查图文与风格一致性，不统一的图片已修改并检查通过；已标记图片符合跳过复查的条件。
- [ ] 修改并检查通过的图片带 `_revised` 标记，全部引用和相关生成脚本的输出路径已同步更新。
- [ ] 文件命名与目录便于定位，确实混乱的命名已整理；不是仅凭能够编译就认定组织清楚。
- [ ] 文件包含关系和交叉引用已检查，重复或循环包含、失效路径、重复标签、未定义或错误引用已修复，全部调用方同步更新。
- [ ] 源码及标题、列表、表格、图注、代码块格式协调，影响阅读或排版的混乱已整理，代码、公式和命令含义保持正确。
- [ ] 示例与小项目按正文命令实际构建、运行，结果支持讲解；未运行或只做静态检查的部分单独列为未完成。
- [ ] 按项目构建方式编译至引用与编号稳定，没有缺失文件、未定义引用或影响阅读的排版问题；受影响的 PDF 页面已实际检查，修改共享模板时检查其他受影响卷。

## 输出要求

- 直接输出修改后的完整 `.tex` 文件内容或 diff，不要省略中间段落。
- 新增内容与上下文风格协调。命令、文件名和路径通常使用代码环境、`\texttt`、`\verb` 或 `\path`，按转义需要选择；数学表达式才用数学环境，不把所有命令机械放进 `$...$`。
- 优先沿用现有主文件和共享模板；为解决明确的结构、引用或排版问题，可以修改 `main.tex`、章节层级映射和模板。同步更新相关引用，检查对其他章节或卷的影响，不因这些文件承担全局作用而一律禁止修改。
- 完成后说明：新增了哪些结构要素、改造了哪些原有内容、是否有因信息不足而留待人工补充的位置。
- 交付时附逐项检查结论，可用简短列表或状态表；等效实现、题量调整、不适用项和未完成项必须说明依据。不能只写“已按规范整理”或在存在未完成项时宣称全部检查通过。
- 若整理了 LaTeX 文件，列出重命名或移动的旧路径 → 新路径、引用结构与格式调整内容，以及编译和 PDF 排版检查结果。
- 若新增或修改了演示项目，说明项目路径、对应概念、正文讲解位置及构建运行验证结果。
- 若修改了图片，列出原文件名 → 带 `_revised` 标记的新文件名、风格调整内容及检查结果，便于后续识别已整理图片。
